# 字体 × 傅里叶：小短横的成因与「傅里叶体」

> 结论先行：**是字体的问题，但换字体只能解决一半；另一半是几何问题，已经用支线剪枝修掉了；根治方案是做一套「骨架字体」，也就是你要的傅里叶体。**

---

## 1. 那些小短横到底是什么

不是渲染噪点，也不是傅里叶的锅。它们是**骨架化（medial axis）对笔画端部「顿角」的忠实翻译**。

宋体横画的起笔有一个三角形顿角。把它二值化、细化成 1px 中线时，这个三角形的中轴不是一条线，而是一条主线 + 一条分叉出去的短线。短线被追踪成独立笔画，画出来就是一根悬空的小横线。

字体里的三种端部，会产生三种碎枝：

| 端部类型 | 例子 | 碎枝 |
|---|---|---|
| 顿角 / 衬线（三角形） | 宋体、仿宋、楷体 | 最严重，一条 10–30px 的平行支线 |
| 收笔渐细（brush taper） | 行楷、隶书 | 中段塌陷 + 末端发丝 |
| 圆端 / 平端 | 幼圆、黑体 | 几乎没有 |

## 2. 实验：12 种字体的同一字「永」

方法：400px 栅格化 → Zhang-Suen 细化 → 骨架追踪。统计「长度 < 字高 6% 的段」占比（即碎枝率）。

| 字体 | 段数 | 碎枝率 |
|---|---|---|
| **幼圆** | 77 | **2.4%** ← 最低 |
| 华文行楷 | 73 | 4.0% |
| 等线 | 95 | 5.3% |
| 仿宋 | 103 | 5.4% |
| 黑体 | 75 | 5.6% |
| 宋体 | 94 | 5.6% |
| 微软雅黑 | 88 | 6.3% |
| 华文细黑 | 83 | 7.3% |
| 楷体 | 75 | 7.6% |
| Noto Sans SC | 80 | 7.6% |
| 华文宋体 | 91 | 9.0% |

见 `fonts.png`（骨架对照）与 `font-compare.png`（完整绘制对照）。

**观察**：

- 行楷（行书）**并不更干净**。它的碎枝率只比宋体低一点，骨架还更"飘"——因为毛笔的起收笔是一团厚墨，中轴在厚处会乱走。行书好看是好看，但它解决的是气质问题，不是碎枝问题。
- 真正决定碎枝的是**端部形状**：圆端 > 平端 > 顿角 > 毛笔收笔。

## 3. 换字体能解决吗：能缓解，不能根治

三条路，颗粒度不同：

### A. 换字体（今天就能做，解决 30–50%）
挑圆端或平端的等线体。实测**幼圆**的碎枝最少，但它是"儿童圆体"，气质偏软，和前卫的仪器感不搭；**等线/黑体**更克制，碎枝中等。

已做：界面右下角加了 `宋 黑 等 圆 楷 行` 六个切换，可以现场比。

### B. 算法清理（已实现，解决 ~90%）
`geom.pruneSpurs()`：从骨架的每一个自由端出发走，如果不到 `5.5% 字高` 就撞上交叉点，判定为碎枝并整条删除；迭代到收敛。

注意它**不会误杀真笔画**：独立的点（如"永"的丶）走不到交叉点，会被保留。

对照见 `font-compare-3.png`：宋体的小短横全部消失，字形变成一个干净的细线骨架。这一条对所有字体都有效，包括行楷。

## 4. 傅里叶体：它不应该是「字体」，应该是「骨架数据」

这是这次研究最重要的判断。

**为什么不做传统字体**：传统字体存的是**轮廓**（填充区域）。我们的流水线永远是「轮廓 → 骨架 → 中线」，也就是先扔掉一半信息再猜回来。碎枝、抖动、粗细造成的偏移，全部来自这一步猜测。

**傅里叶体应该直接存中线**：每个字 = 若干条有序的、带方向的骨架折线。这样：

| | 传统字体 | 傅里叶体（骨架数据） |
|---|---|---|
| 流水线 | 栅格 → 二值 → 细化 → 追踪 | 直接读 |
| 碎枝 | 必然产生 | 结构上不存在 |
| 耗时 | 80–120ms/字 | ~0ms |
| 跨系统 | 依赖本地字体 | 完全一致 |
| 粗细 | 影响骨架 | 无影响 |

### 4.1 规格（v0）

```
upem 2000
char : { strokes: [ { d: "M x y L x y ...", w: 100 } ] }
```

- **单线**：无宽度概念，笔宽由渲染决定（当前 1.45px）。
- **圆端、圆角**：所有端点 round cap；所有转角最小半径 **0.03em**。
  → 这条是给傅里叶用的：尖角在频谱里是无限高频，圆角后同样的 K 保真度能高一个数量级。
- **笔画有序**：数组顺序 = 书写顺序；每笔的首点 = 起笔点。
- **可选连笔层**：`join: [[0,1],[2,3]]` 表示第 0 笔末点可直接连到第 1 笔首点（行书式），用于减少抬笔。
- **拐角词汇**：横竖相交处不切断，走"直行穿过"——与现在的追踪策略一致。

### 4.2 生成流水线

```
开源等线体（Noto Sans SC / 霞鹜文楷，OFL 授权）
  → 1024px 栅格化
  → 细化
  → 支线剪枝（本节 B）
  → 交叉点按最小转角合并成笔画
  → Chaikin 圆角 + 三次贝塞尔拟合（圆角半径 0.03em）
  → 笔画排序（书写顺序启发式：先横后竖、先上后下、先左后右）
  → 序列化为 JSON
```

**授权注意**：宋体/幼圆/微软雅黑都是商业字体，派生数据不能分发。必须从 OFL 字体（Noto Sans SC、霞鹜文楷）派生，或者手绘。

### 4.3 覆盖策略

- **常用 3500 字**离线预生成，JSON 约 1.2MB，gzip 后 ~300KB，首屏按需加载。
- 字表外的字**回落到运行时骨架化**（现在的流水线，已带剪枝），保证"什么字都能画"。
- 拉丁字母/数字：手绘 62 个单线字形，工作量很小，且单线拉丁极其优雅。

## 5. 现在的状态（v1.3）

- ✅ 支线剪枝已进流水线，宋体的小短横消失
- ✅ 界面加了七个字面（宋/黑/等/圆/楷/行 + 傅里叶体）
- ✅ **傅里叶体 v0 已落地**：558 字，运行时按字排版，缺字自动回补

### 5.1 实现

```
tools/gen.html        离屏生成器：字表 → 每字骨架 → em 坐标（1000 upem）
tools/merge.js        合并分片 → app/data/fourier-font.js（window.EP_FONT）
geom.charStrokesEm()  单字 → em 坐标系（y 向下，字面居中）
geom.layoutEm()       多字按 em 方框排布 → 统一归一化 → 傅里叶流水线
app.fourierPath()     先查表，查不到现场生成同规格骨架
```

数据格式：`{ v:1, upem:1000, chars: { "永": [[[x,y],...], ...] } }`，558 字 ≈ 550KB。

### 5.2 过程中修掉的一个真 bug

栅格化会把字形裁到紧贴图像边缘，而 Zhang-Suen 细化、骨架追踪都假设四周有 1px 背景。
结果是：**「一」整条消失、竖画笔直的字形根本细化不动**。加了 2px padding 后修复。
这个 bug 影响的不只是傅里叶体，所有字体路径都受影响——之前「山」少一竖就是这个原因。

### 5.3 尚未解决

- 笔画在交叉点处的收尾仍会被级数向内"收"一点，现在用端点外延 14 单位补偿，够用但不精确。
- 没有连笔层（`join`），抬笔次数还是一次一笔。
- 只有 558 字，超出范围回落到现场生成（同规格，会慢 ~80ms/字）。
- 笔画顺序是启发式，不是真正的书写顺序。
